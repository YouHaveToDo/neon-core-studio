# 소수점 데미지/HP 제안서 (Fractional Damage & HP Proposal)

**상태: 제안 — 미승인.** CEO 확정 사항이 아니다. `js/state.js`의 `applyWeakenToDamage()`가
`Math.floor(rawDamage * 0.75)`로 항상 내림 처리하는 것("10 데미지 × 0.75 = 7.5 → 7로 내림")이
불공정하다는 CEO 문제 제기에서 시작됐다. CEO는 "Weaken만 내림 대신 반올림으로 바꾸는" 더 작은
대안 대신 **"게임에 소수점 HP/데미지를 도입한다"는 더 큰 방향을 명시적으로 선택**했다 — 이 문서는
그 선택을 실제로 구현 가능한 스펙으로 설계하는 동시에, 그 선택의 실제 비용을 CEO가 완전한 정보를
갖고 재확인할 수 있도록 두 옵션을 나란히 제시한다.

**참고한 자료**: `js/state.js`(데미지 파이프라인 전체, `applyWeakenToDamage`/`dealDamage`/
`applyDamage`/`applyBlock`), `js/data.js`(`CARD_DEFS`/`EXPANSION_CARD_DEFS`, `PLAYER_START`),
`js/ui.js`(HP/방어도/마나 렌더링), `docs/design/gameplay-depth-proposal.md` §2.5(밸런스 수치),
`docs/design/card-shop-currency-proposal.md` §3(Weaken 정의, 이미 승인/구현/QA 완료된 스펙),
`docs/design/art-direction.md` §2(숫자 타이포그래피 규칙).

## 0. 결론 먼저 — TL;DR

1. **내가 실제로 추천하는 안은 "Option A: 내림 대신 반올림, 상태는 계속 정수"다.** 아래 §4의 수치
   분석으로 증명하듯, 이 게임의 현재 카드 데이터 구조상 Weaken이 만드는 소수점은 **항상 정확히
   .5(반) 하나뿐**이고, 내림을 반올림으로 바꾸는 것만으로 CEO가 지적한 "매번 내림당하는" 불공정을
   **100% 정확히 상쇄**한다(90%가 아니라 정확히 전부). 엔진 변경은 `js/state.js` 단 1줄이고, UI/표시
   문제 자체가 생기지 않는다(정수 상태가 계속 정수로 남으므로).
2. **그럼에도 CEO가 이미 "진짜 소수점 HP/데미지"를 명시적으로 선택했으므로, 그 옵션(Option B)도
   완결된 스펙으로 아래 §5-§7에 전부 설계해뒀다** — Option B를 그대로 확정해도 프로그래머에게 바로
   넘길 수 있다.
3. **Option B의 실제 비용은 "포뮬러 한 줄"이 아니다.** HP뿐 아니라 **방어도(Block)도 소수점 상태가
   될 수 있다**는 점을 이번 감사 과정에서 새로 확인했다(§5.3) — 방어도가 소수 피해를 부분 흡수하면
   방어도 자체가 소수로 남는다. HP/방어도 텍스트, 데미지/방어도/회복 팝업 등 `js/ui.js`의 렌더링
   지점 다수를 손봐야 하고, "HP/방어도가 정수"라는 이 게임의 지금까지의 암묵적 불변조건 자체가
   영구히 깨진다 — 이미 승인·QA 완료된 `card-shop-currency-proposal.md` §3의 스펙 문구("내림
   처리")도 함께 개정해야 한다. 작지 않은, 그러나 감당 못 할 정도로 크지도 않은 작업이다(§6).
4. **§2.5(gameplay-depth-proposal.md)의 기존 밸런스 결론은 이 변경으로 전혀 재검토 대상이 아니다**
   — §2.5의 모든 수치(Quick Guard vs Defend, Iron Skin/Bloodlust 회수량, Execute+Bloodlust
   버스트)는 Weaken이 도입되기 *전*에 작성된 문서라 애초에 `applyWeakenToDamage()`를 한 번도 거치지
   않는다(§4.1에서 확인).

## 1. 배경 — 지금 무슨 일이 일어나고 있나

`js/state.js:608-610`:

```
function applyWeakenToDamage(actor, rawDamage) {
  return actor.weaken > 0 ? Math.floor(rawDamage * 0.75) : rawDamage;
}
```

`card-shop-currency-proposal.md` §3.1(이미 승인·구현·QA 통과된 스펙)은 이 동작을 "25% 감소,
**내림 처리**"라고 명시적으로 규정했다. 즉 지금의 내림 동작은 버그가 아니라 승인된 스펙대로다 —
다만 CEO는 그 스펙 결정 자체가 불공정하다고 재검토를 요청한 것이다.

## 2. 소수점은 어디서 생기고, 지금 어디서 멈추는가

### 2.1 카드 자체 수치는 전부 정수 — 확인함

`js/data.js`의 `CARD_DEFS`(14종, 9-73행)와 `EXPANSION_CARD_DEFS`(8종, 112-145행)를 전부 직접
읽어 확인했다. 데미지/방어도/회복/드로우 수치는 예외 없이 정수다:

| 카드 | 데미지/방어도/회복 |
|---|---|
| Strike | 6 |
| Heavy Slash | 14 |
| Twin Strike | 4×2 |
| Piercing Strike | 10 |
| Execute | 10(+10) |
| Reckless Swing | 12(자해 3) |
| Defend / Quick Guard / Fortify / Steady Breath | 5 / 4 / 10 / 3 (방어도) |
| Second Wind | 6 (회복) |
| Enfeeble / Crippling Blow / Exploit Weakness / Overextend / Crushing Curse | 0 / 8 / 8(+8) / 10 / 4 |
| Bloodlust 보너스(`attackBonus`) | 스택당 +2 |

`PLAYER_START`(`maxHp: 50, maxMana: 3`)도 정수. **소수를 만드는 지점은 코드 전체에서
`applyWeakenToDamage()`의 `× 0.75` 단 한 곳뿐**이라는 과업 지시의 전제는 실제로 맞다.

### 2.2 결정적으로 중요한 추가 발견 — 소수는 항상 정확히 "반(.5)"뿐이다

Weaken 배율이 적용되는 값(`rawDamage` = 카드 기본 데미지 + 카드별 조건부 보너스 + Bloodlust
보너스)은 **현재 카드 데이터상 항상 짝수**다 — 모든 Attack 카드의 기본 데미지가 짝수(6, 14, 4, 10,
20, 12, 0, 8, 16, 10, 4)이고 Bloodlust 보너스도 스택당 +2로 항상 짝수이기 때문이다. 짝수 × 0.75는
수학적으로 정수 또는 정확히 "정수 + 0.5" 둘 중 하나만 나올 수 있다(x=2y일 때 x×0.75=1.5y — y가
짝수면 정수, 홀수면 정확히 .5). **.25나 .75 같은 다른 소수점은 지금 카드 풀에서 구조적으로 나올 수
없다.** 이 사실이 §4의 밸런스 분석과 §3의 대안 설계 둘 다의 근거가 된다.

## 3. Option A (추천) — 내림 → 반올림, 상태는 계속 정수

### 3.1 규칙

`applyWeakenToDamage()`를 아래로 바꾼다(내림 대신 **반올림, 사사오입/round-half-up**):

```
actor.weaken > 0 ? Math.round(rawDamage * 0.75) : rawDamage
```

JS의 `Math.round()`는 우리 도메인(데미지는 항상 0 이상)에서 정확히 "반올림 시 .5는 위로"로
동작하므로 별도 반올림 함수가 필요 없다. **HP/방어도/마나 등 어떤 상태도 정수 상태를 벗어나지
않는다** — `applyWeakenToDamage()`가 반환하는 순간 이미 정수이므로, 이후 파이프라인(방어도 차감,
HP 적용, `js/ui.js` 렌더링) 전부 지금과 완전히 동일하게 동작한다.

### 3.2 왜 이게 "90%"가 아니라 "100%" 해결인가

§2.2에서 증명했듯 지금 카드 풀에서 Weaken이 만드는 소수는 항상 정확히 .5다. 내림은 .5를 무조건
버려서 항상 공격자에게 정확히 0.5 데미지 손해를 준다. 반올림(사사오입)은 .5를 무조건 올려서 그
0.5를 정확히 되돌려준다 — "가끔 위로, 가끔 아래로 반올림돼서 평균적으로 공평해진다"는 확률적 정당화가
아니라, **지금 데이터로는 100%의 케이스에서 정확히 원래 손해분만큼 정확히 상쇄된다**는 결정론적
사실이다. CEO가 든 예시("10 데미지 × 0.75 = 7.5 → 내림 7") 그대로 검증됨: 반올림하면 7.5 → 8,
정확히 손해 없음.

### 3.3 이 안의 한계 (정직하게 밝힘)

- 미래에 홀수 기본 데미지를 가진 카드가 추가되면(.25/.75 같은 소수 발생 가능) 반올림이 §2.2의
  "100% 정확히 상쇄" 성질을 잃는다 — 다만 그래도 "항상 내림"보다는 항상 공평하다는 성질(장기적으로
  기댓값 편향 0)은 유지된다.
- "진짜 소수점 HP/데미지"라는 CEO의 명시적 요청 문구를 문자 그대로 만족시키지는 않는다 — HP는
  여전히 항상 정수다. CEO가 "정수로 반올림당하는 것 자체"가 아니라 "매번 아래로만 깎이는 것"에
  반응한 것이라면 이 안으로 충분하지만, "HP가 진짜로 43.5 같은 값에 머무는 게임"을 원한 것이라면
  이 안은 그 요청을 만족시키지 않는다 — 이건 CEO만 답할 수 있는 지점이라 §8에 열어둔다.

## 4. §2.5 기존 밸런스 결론에 대한 영향 — 정량 분석

### 4.1 결론: `gameplay-depth-proposal.md` §2.5는 전혀 재검토 대상이 아니다

§2.5는 Weaken이 존재하기 전에 작성된 문서다(`card-shop-currency-proposal.md`가 그 뒤에 §2.1을
이어받아 Weaken을 신규 도입). §2.5가 다루는 세 계산—Quick Guard vs Defend, Iron Skin/Bloodlust
회수량, Execute+Bloodlust 버스트—전부 `applyWeakenToDamage()`를 한 번도 거치지 않는 순수 정수
카드 값 비교다. Weaken의 반올림/내림 방식을 바꾸는 것은 이 세 계산의 전제 자체를 건드리지 않으므로
숫자가 단 하나도 바뀌지 않는다.

### 4.2 실제로 영향받는 것은 `card-shop-currency-proposal.md` §3/§4.3뿐이다

내림이 만드는 실제 편향을 처음으로 정량화한다(mod-4 분석, Bloodlust 스택 수 `b`에 따른 짝/홀 반영):

| 카드 | 원값(step1+2) | b=0일 때 내림 손해 | b=1일 때 내림 손해 |
|---|---|---|---|
| Strike | 6+2b | 0.5 | 0 |
| Heavy Slash | 14+2b | 0.5 | 0 |
| Piercing Strike | 10+2b | 0.5 | 0 |
| Execute (조건 미충족) | 10+2b | 0.5 | 0 |
| Overextend | 10+2b | 0.5 | 0 |
| Twin Strike (각 타격) | 4+2b / 4 | 0 | 0.5 |
| Execute (조건 충족) | 20+2b | 0 | 0.5 |
| Reckless Swing | 12+2b | 0 | 0.5 |
| Crippling Blow | 8+2b | 0 | 0.5 |
| Exploit Weakness | 8(+8)+2b | 0 | 0.5 |
| Crushing Curse | 4+2b | 0 | 0.5 |

손해는 **항상 정확히 0이거나 정확히 0.5**다 — 절대 그 이상이 아니다. `card-shop-currency-
proposal.md` §4.3이 이미 "약화의 최대 페널티(-25%)는 Execute+Bloodlust 콤보가 만드는 스윙(HP 50
기준 25~30뎀)보다는 훨씬 작은 변동폭"이라고 결론 내렸는데, 지금 밝혀진 내림 편향(타격당 최대 0.5)은
그 이미 "훨씬 작다"고 판정된 수치보다도 두 자릿수 이상 더 작다. **결론: 이 변경이 §4.3의 플레이테스트
플래그를 재검토하게 만들 정도의 크기가 아니다.** 유일하게 실제로 수정이 필요한 것은
`card-shop-currency-proposal.md` §3.1의 "내림 처리"라는 스펙 문구 자체다(§8에서 별도 정리).

## 5. Option B — 진짜 소수점 HP/방어도 (CEO가 이미 선택한 방향)

과업 지시가 명시한 대로, CEO가 이미 "Weaken 한정 반올림"보다 큰 방향을 선택했다는 전제 하에
완결된 스펙을 아래에 설계한다.

### 5.1 규칙 — 파이프라인 어디서도 반올림/내림하지 않는다

```
actor.weaken > 0 ? rawDamage * 0.75 : rawDamage
```

`Math.floor`/`Math.round` 둘 다 제거한다. 이 값은 그대로 5단계 파이프라인(방어도 차감 → HP 적용)을
소수인 채로 통과하며, **그 어느 단계에서도 정수로 반올림되지 않는다.** "진짜 소수점 정밀도"라는
요청을 문자 그대로 구현하는 방식이 이것이다.

### 5.2 어떤 상태가 소수점을 영구히 가질 수 있는가 — 이게 이 설계의 핵심

- **HP: 그렇다, 영구적으로.** `target.hp`는 매치 종료(또는 정수 값으로 우연히 되돌아올 때, 예:
  회복 카드가 `maxHp`(항상 정수)에서 캡되는 경우)까지 소수로 남을 수 있다. `state.player.hp`가
  턴 사이에도 예컨대 `43.5`인 채로 유지된다.
- **방어도(Block): 그렇다 — 이번 감사에서 새로 발견한 사실.** 과업 지시 문서는 "HP가 소수가
  되는가"만 물었지만, `dealDamage()`(`js/state.js:535-544`)를 추적하면 방어도도 소수 상태가 될 수
  있다는 게 드러난다(§5.3 예시 2). 방어도가 소수 데미지를 *부분적으로만* 흡수하면(방어도 잔량이
  들어오는 소수 데미지보다 큰 경우) `target.block -= absorbed`의 `absorbed`가 소수이므로 방어도
  자체가 소수로 남는다.
- **마나: 아니다.** 마나는 카드 비용(항상 정수)만 차감하며 Weaken 파이프라인을 절대 거치지 않는다
  — 변경 없음.
- **Weaken 스택 수 자체: 아니다.** 스택은 항상 정수로 부여/감소한다 — 변경 없음.
- **카드 비용/타입/기타 정적 데이터: 아니다.** `js/data.js`는 전혀 수정하지 않는다.

### 5.3 전체 예시 두 개 — 정확히 무엇이 어떤 형태로 남는지

**예시 1 (과업 지시가 든 예시, 방어도가 완전히 소진되는 경우)**: 공격자가 Weaken 상태, 기본
10데미지 카드 + Bloodlust 2스택(+4) → step1+2 합계 14 → Weaken 배율 적용 `14 × 0.75 = 10.5`(소수
발생 시작점) → 대상 방어도 5 → `Math.min(5, 10.5) = 5`(방어도는 전부 소진, 정수 0으로 남음) →
남은 데미지 `10.5 - 5 = 5.5` → `target.hp -= 5.5`. **이 시점부터 대상의 HP는 영구히 소수 상태다**
(예: 50.0 → 44.5). 방어도는 이 경우 우연히 정수(0)로 남았다.

**예시 2 (방어도가 소수를 남기는 경우, 새로 발견한 케이스)**: 위와 같은 10.5 소수 데미지가 발생했는데
대상의 방어도가 20(과잉 방어)이라면 `absorbed = Math.min(20, 10.5) = 10.5`(방어도가 소수 데미지를
전부 흡수하되 그 자체가 소수), `target.block = 20 - 10.5 = 9.5`. **방어도도 이 순간부터 소수
상태로 남는다** — HP는 이번엔 전혀 깎이지 않았는데도.

### 5.4 표시(Display) 규칙 — "화면에는 반올림, 내부는 정밀 유지"

**추천: 내부 상태는 완전한 소수 정밀도를 유지하되, 화면에 표시되는 모든 숫자(HP 텍스트, 방어도
텍스트, 데미지/방어도/회복 팝업)는 반올림(사사오입)한 정수로만 보여준다.**

근거:
- `art-direction.md` §2는 HP/마나/데미지 숫자를 `font-variant-numeric: tabular-nums` 고정폭
  숫자로 규정하고, §3 카드 스펙의 모든 효과 텍스트는 예외 없이 정수("6 데미지", "방어도 5 획득")로
  쓰여 있다. 이 다크 판타지 카드 게임의 지금까지의 숫자 언어는 전부 "깔끔한 정수"다. 그 언어 한복판에
  갑자기 "-7.5" 데미지 팝업이나 "43.5 / 50" HP 바가 등장하면, 그게 의도된 정밀도라는 걸 플레이어가
  알 방법이 없다 — 오히려 "카드 설명은 다 정수인데 왜 화면 숫자만 소수야?"라는 버그처럼 읽힐
  위험이 크다. 이건 "수학적으로 더 정확한 쪽"이 항상 "더 나은 플레이어 경험"은 아니라는 사례다.
- 반면 내부 상태를 정밀하게 유지하는 건 순수 이득이다 — Execute의 처형 조건
  (`target.hp / target.maxHp <= 0.3`)처럼 HP 비율을 검사하는 로직이 있으면 오히려 더 정확해진다
  (지금은 정수 HP라 이 조건 판정 경계에서 이미 약간의 반올림 오차가 존재했는데, 소수 HP를 내부에서
  그대로 유지하면 이 오차가 사라진다 — 부수적 이득으로 기록).
- **알려진 부작용(사소하지만 밝혀둠)**: 화면의 "HP 바 표시값 변화량"과 "데미지 팝업 숫자"가 반올림
  오차 때문에 서로 정확히 일치하지 않을 수 있다(예: 44 → 39로 표시되는데 팝업은 "-4"만 뜨는 식,
  최대 오차는 §2.2에 따라 현재 카드 풀 기준 0.5 이내로 유계). 많은 게임이 이미 겪는 흔한 현상이라
  치명적이진 않지만, QA가 "숫자가 안 맞는다"고 오인하지 않도록 미리 문서화해둔다.

### 5.5 코드 영향 범위 (프로그래머 참고용 — 구현은 프로그래머 담당, 이 문서는 스펙만)

- `js/state.js`: `applyWeakenToDamage()`에서 `Math.floor` 제거(1줄). `dealDamage`/`applyDamage`/
  `applyBlock`/HP 관련 비교(`<= 0`, `/maxHp <= 0.3`)는 부동소수점과 이미 호환되므로 로직 자체는
  무수정.
- `js/ui.js`: `renderBattle()`의 `opponentHpText`/`playerHpText`/`opponentBlockText`/
  `playerBlockText` 4곳, `handleFx()`의 데미지/방어도/회복 팝업 텍스트 조립 지점 — 전부 반올림
  래퍼를 거치도록 수정 필요. 대략 6~8개 렌더 지점.
- 네트워크 동기화: 별도 작업 불필요로 판단 — `state.opponent`는 실제 HP 값을 와이어로 전송받는 게
  아니라 양쪽 클라이언트가 동일한 `applyCardEffect()`를 로컬에서 재생해 같은 결과를 얻는 구조(파일
  헤더 및 `applyRemoteCardPlay()` 참고)이므로, 두 클라이언트의 JS 엔진이 동일한 단순 부동소수점
  연산(곱셈/뺄셈)에 대해 IEEE754 표준을 따르는 한 자동으로 동기화된다. 이론적으로는 부동소수점
  결정성 리스크가 0은 아니라는 점만 각주로 남긴다(실제 위험도는 낮음).
- **문서 개정 필요**: `card-shop-currency-proposal.md` §3.1의 "25% 감소 (내림 처리)"라는 이미
  승인·구현·QA 완료된 스펙 문구를 "내림 없이 소수점 그대로 유지(화면 표시는 반올림)"로 개정해야
  한다 — 이건 그린필드 기능이 아니라 이미 출시되고 QA 통과된 동작을 뒤집는 것이므로, 승인 시
  `docs/qa/card-shop-currency-milestone.md`에도 "동작 변경, 재검증 필요"로 플래그해야 한다.

## 6. 정직한 스코프/비용 평가 (`CLAUDE.md` "과도한 스코프 금지" 원칙)

| 항목 | Option A (반올림, 정수 유지) | Option B (진짜 소수 HP/방어도) |
|---|---|---|
| 엔진 변경 | `js/state.js` 1줄 | `js/state.js` 1줄(내용은 다름 — floor/round 제거) |
| UI 변경 | 없음 | `js/ui.js` 6~8개 렌더 지점에 반올림 래퍼 적용 |
| 게임의 핵심 불변조건 | 안 바뀜(HP/방어도는 계속 항상 정수) | **영구히 바뀜** — "HP/방어도는 정수"라는 지금까지 암묵적 전제가 깨져서, 앞으로 추가되는 모든 카드/기능이 이 사실을 알고 설계돼야 함 |
| 이미 승인된 스펙 문서 개정 | `card-shop-currency-proposal.md` §3.1 단어 하나만("내림"→"반올림") | 같은 절, 문장 자체를 다시 씀 + QA 재검증 플래그 |
| CEO가 지적한 "불공정" 해결도 | **100%**(§3.2, 현재 카드 데이터 기준 결정론적으로 증명됨) | 100% (근본적으로 편향을 없애는 방식이므로 당연히 해결) |
| "진짜 소수점"이라는 문자 그대로의 요청 충족 여부 | 아니오 (HP는 항상 정수로 남음) | 예 |
| QA 재검증 표면 | 거의 없음(Weaken 관련 회귀 테스트만) | 다중 타격(Twin Strike)/방어도 부분 흡수/화면-팝업 불일치 등 새 케이스 검증 필요 |

**결론**: Option B가 "invasive"라고 부를 만큼 크지는 않다(카드 데이터 무수정, 새 상태 필드 불필요,
네트워크 직렬화 변경 불필요) — 하지만 "포뮬러 하나만 고치면 끝"도 절대 아니다. 실질 비용은 (1)
`js/ui.js`의 여러 렌더 지점을 손보는 기계적이지만 놓치기 쉬운 작업, (2) 이 게임의 HP/방어도가
"항상 정수"라는 사실을 영구히 포기한다는 설계적 결정 — 이후의 모든 카드/기능이 이걸 감안해야 한다.
Option A는 그 두 비용을 전부 피하면서 §3.2에서 증명했듯 CEO가 실제로 지적한 문제(매번 아래로만
깎이는 것)를 정확히 100% 해결한다.

  범위)를 그대로 구현 스펙으로 사용. `card-shop-currency-proposal.md` §3.1 개정 + QA 재검증 플래그
  동반.

## 8. CEO 확인이 필요한 열린 질문

1. **Option A vs Option B**: §3.2/§4.2가 증명하듯, 현재 카드 데이터 기준으로는 Option A가
   "매번 아래로만 깎인다"는 원래 문제 제기를 수학적으로 완전히(100%) 해결한다. 그럼에도 "HP가 실제로
   43.5 같은 값에 머무는 게임"이라는 문자 그대로의 요청이 진짜 목표라면 Option B가 필요하다 — 어느
   쪽이 실제로 원하시는 경험인지 확인 부탁드린다. (이미 Option B로 방향을 정하셨다면 그대로 진행해도
   되고, 이 표를 보고 Option A로 낮춰도 된다 — 둘 다 이 문서 안에서 바로 승인 가능한 완결 스펙이다.)
2. **Option B를 택할 경우, 화면 표시 반올림 규칙(§5.4)에 동의하는가**, 아니면 실제 소수점을 화면에도
   그대로 노출하고 싶은가(예: "43.5 / 50")? 후자를 원한다면 art-direction.md의 숫자 타이포그래피
   언어를 재검토해야 하므로 아티스트에게 별도 브리프가 필요하다.
3. **Option B를 택할 경우, 미래 카드 설계 제약을 감수하는가**: 앞으로 추가되는 카드도 "HP/방어도가
   소수일 수 있다"는 전제를 깨지 않아야 한다(예: "정확히 절반 회복" 같은 카드 텍스트를 설계할 때
   반올림 방식을 명시해야 함). 지금 8종 확장 풀에는 해당 없음 — 향후 카드 확장 시 유의 사항으로만
   플래그.

승인 시 프로듀서에게 작업 분해를 넘기고, 확정된 옵션에 따라 §7의 핸드오프 스펙을 프로그래머에게
전달할 준비가 되어 있다.
